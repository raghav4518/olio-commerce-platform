## 5. Cross-panel invariants

1. A single ebook has one canonical internal ID and stable public slug; each panel renders the same title, cover, contributor attribution, price/currency and publication state as appropriate.
2. Customer can access only their own profile, bag, orders, invoices, library, reading state, wishlist, reviews, notifications and tickets.
3. Admin and Support use distinct staff authorization contexts. No customer session can become staff by editing client state.
4. Support customer-facing ticket APIs return public conversation entries only. Internal notes require a dedicated staff-only data contract.
5. Payment is a separate record from order status. Pending/failed attempts cannot create paid entitlements.
6. An entitlement is a separate persistent grant with source, owner, ebook/file version, status, timestamps, grant/revoke reason and audit reference.
7. Finance values are computed from verified transactions and ledger/reconciliation records, not from sample cards or client-side totals.
8. All list views use server-side filtering/sorting/pagination at realistic scale.
9. Every mutation validates input and permissions on the server, persists to the authoritative database, emits audit/event records as appropriate and returns a canonical response.
10. Frontend status labels should be mapped from canonical domain enums; do not create conflicting per-panel state machines.


## 6. Required screen-state coverage

For each route, implement relevant loading, empty, error, unauthorized/forbidden, success, pending, stale-data and retry states. A page may omit irrelevant states, but the decision must be explicit in the screen test matrix. Payment screens are server-state projections, not separate client-authored payment states. File uploads must show selected/uploading/scanning/accepted/rejected/retry states. Destructive actions require confirmation and success must be shown only after the server confirms persistence.


## 7. Screen acceptance evidence

The implementation agent must maintain `SCREEN-INVENTORY.csv` with added columns for implemented route, component file(s), API operation IDs, permission, tests, responsive verification, status and evidence link. No row may be silently removed. A page may be consolidated into a shared responsive component only if the same user-visible coverage and route/state behaviour remains available.
